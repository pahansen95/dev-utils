Below are some considerations and next steps for implementing c_clone_process:

• Use clone_args to mimic a simple “fork.”  
  – No CLONE_THREAD, CLONE_SIGHAND, or CLONE_VM. This ensures a truly separate process with its own memory space, signals, and file descriptors.  
  – Typically, you’ll want exit_signal = SIGCHLD, which is the usual fork/exit behavior so that the parent can wait for the child.  

• Construct the struct clone_args carefully:  
  – stack / stack_size: The child needs its own stack pointer. If you want to handle the entire process memory manually, ensure you specify a properly allocated stack region or pass NULL and rely on copy-on-write (like normal fork).  
  – flags: Ensure you zero out bits you won’t use (e.g., no CLONE_FILES if you want a wholly separate descriptor table).  

• For unneeded descriptors in the child, close them in userland right after clone3 returns in the child code path. For completeness, if you isolate file descriptors, avoid CLONE_FILES so that the child inherits a copy of the parent's FD table, which you can prune in the child.  

• Program flow in c_clone_process might look like this:  
  1. Build a clone_args struct, zero all fields.  
  2. Fill out clone_args.exit_signal = SIGCHLD (or whichever signal is appropriate).  
  3. Possibly set specific flags to get a new FS or new Files if needed, but typically not.  
  4. Optionally define a separate stack for the child. If you pass stack = NULL and stack_size=0, you get the old “share parent stack with copy-on-write” style (careful with multithreading).  
  5. Call syscall(SYS_clone3, &clone_args, sizeof(clone_args)).  
  6. If syscall returns 0, you’re in the child—clean up unneeded FDs, proceed to execve. If > 0, you’re in the parent—return the new PID. If < 0, handle the error.  

• Validate corner cases, e.g. if the user sets a bizarre set of flags or tries to skip stack assignment while multi-threaded.  

• After c_clone_process returns in the parent, you can “fork-like” handle signals or do a wait. In the child, you can finalize environment setup and then call execve.  

Summary:  
Careful assignment of clone_args, clearing flags that might cause the child to share resources, and closing unneeded descriptors in the child path are key to a minimal “fork-like” behavior.

````c
/* A function that returns the child's PID or -1 on error */
/* Example "fork-like" usage of clone3() */
static pid_t fork_like_clone3(void) {
    struct clone_args cargs;
    /* Zero-initialize the entire struct for safety */
    memset(&cargs, 0, sizeof(cargs));

    /* 
       We want the standard SIGCHLD signal on child exit, just like fork. 
       That is placed into clone_args.exit_signal. 
       Then we keep a minimal flags=0 for an independent process 
       (no CLONE_VM, CLONE_THREAD, CLONE_SIGHAND, etc.).
    */

    /* 
       If we provided a separate stack, we’d fill cargs.stack and cargs.stack_size. 
       For this minimal scenario, we omit them, resulting in behavior 
       similar to a normal fork with copy-on-write memory.
    */

    /* 
       No need for pidfd, set_tid pointers, or cgroup at this time. 
       The relevant fields remain zeroed.
    */

    long rc = syscall(SYS_clone3, &cargs, sizeof(cargs));
    if (rc < 0) {
        return -1; /* handle error appropriately */
    }
    return (pid_t) rc;
}
````

Key points:
• exit_signal = SIGCHLD mimics classic fork’s parent–child signaling.  
• flags=0 avoids shared memory or FD tables, so the child has its own copy of the parent’s resources.  
• If the child returns 0, then it’s in the child code path; if > 0, we’re in the parent.  
• This is the bare-minimum structure; you can iterate from here to manage cgroup, stacks, or TID storage.
